# Survey module — decisions & gotchas log

Append-only, same format as root `docs/DECISIONS.md` (see `docs/MODULE_SPEC.md` §9.2). Entries here are scoped to this module only — a platform-wide decision is cross-referenced by its root `Dnn` id, never restated.

| # | Decision | Status |
|---|---|---|
| SURVEY-D1 | **Ownership/access is plain RBAC** (new `survey.*` permission codes in the manifest), not a per-user "my surveys only" model — matches every other module. **Notify emails** (arbitrary admin-typed addresses) are a module-owned exception to root D21 (confirmed with the user: D21 scoped `NotificationsService`'s own targeting, not other modules). **Question types for v1**: short_text, paragraph, single_choice, multi_choice, dropdown, linear_scale, date, time, rating — file upload and question grids explicitly deferred to a fast-follow. | DECIDED (user) |
| SURVEY-D2 | `one_response_per_respondent` is a per-survey, admin-toggleable setting — cannot be a DB unique/partial index (a plain or partial index can't be conditional on a column in a *different* row). The first migration draft (schema-design phase) got this wrong with a partial unique index on `(survey_id, respondent_user_id)`; building the real submit endpoint against the real toggle surfaced the contradiction (a second submission with the toggle off would 500 on a raw Postgres constraint violation before ever reaching application logic). Fixed by dropping the index for a plain lookup index and moving enforcement entirely into `ResponsesService.submitAuthenticated`. Full writeup: root `D66`. | DECIDED |
| SURVEY-D3 | `SurveysService.replaceStructure`'s three `deleteMany` calls originally used a non-UUID sentinel (`['__none__']`) inside `notIn` to mean "nothing to keep" — Postgres rejects a non-UUID literal against a real `uuid` column even inside `NOT IN`, and this is common (any all-text-question survey has zero options; a section can have zero questions) not rare. Fixed with a conditional `where` (omit the `id` filter entirely when the keep-list is empty, rather than faking a value into it). Full writeup: root `D66`. | DECIDED |
| SURVEY-D4 | `ResponsesService.writeResponse` writes its own `audit_log` row **directly** via the real `AuditLogWriter` (injected from `apps/api/dist/core/audit/audit-log.writer`, `@Global()` so no extra module wiring needed), bypassing the usual `@Audit(...)` decorator on the controller. Deliberate: `submitPublic`'s response body carries a one-time raw edit token that must never reach a durable log, and the generic `@Audit` interceptor's fallback (log the whole handler response as `newValue` when no `fetchState` is given) would have logged it — and `fetchState` can't help either, since it never sees a freshly-created row's id, only the request. Same category of exception as `AuthService`'s own direct login/logout audit rows. | DECIDED |
| SURVEY-D5 | `AnswerInputDto.value: unknown` had no `class-validator` decorator at all, so the global `ValidationPipe`'s `whitelist: true` silently stripped every submitted answer's value before any service code ever saw it — a real bug that would have broken every response, in every deployment, forever. Found only via a full real-browser Playwright walkthrough (the report page showed "answered 0 times" despite a visibly-successful `201` submit); invisible to `tsc` and to direct-Prisma smoke tests. Fixed with `@IsDefined()` (permissive on purpose — real per-question-type shape validation happens later, in `ResponsesService.validateAnswerShape`, once the question's real type is known). Full writeup: root `D67`. | DECIDED |
| SURVEY-D6 | `NotificationEmailService` exported from `NotificationsModule` (the one core-file change this module needed) so `notifyEmails` (SURVEY-D1) can reuse the shared mail transport instead of a second parallel mailer, while `notifyOwnerOnSubmit` still goes through the real, D21-compliant `NotificationsService`. Full writeup: root `D64`. | DECIDED |
| SURVEY-D7 | Respondent-facing fill is split into two controllers/endpoint families (`FillController` for a logged-in visitor, `PublicSurveyController` for none) rather than one conditional endpoint — `JwtAuthGuard` never populates `request.user` on a `@Public()` route even when a valid token was sent, so a single handler branching on "am I logged in" is structurally impossible. `TakeSurveyPage.tsx`'s one canonical `/survey/:surveyId` route picks the pair to call from the real `useAuth()` status. Full writeup: root `D65`. | DECIDED |
| SURVEY-D8 | `TakeSurveyPage.tsx`'s `import { resolveVisibility } from '../../backend/logic-engine'` (no extension) resolved, under Vite's real DEV SERVER, to the compiled `logic-engine.js` CommonJS sibling instead of the `.ts` ESM source that sits right next to it (D56's dual-ship convention) — Vite's default `resolve.extensions` checks `.js` before `.ts`. This threw `does not provide an export named 'resolveVisibility'` at runtime the moment the page's code actually executed in a browser; `npm run build`'s Rollup-based production bundling never surfaced it. Found via a real `vite` dev-server + headless-Chromium check done as part of root `DECISIONS.md` D78's own verification (that change made `discovery.ts` load every module's `routes.tsx`, and therefore this page, EAGERLY at app boot instead of only on navigation to `/survey/:surveyId` — turning a latent per-page bug into one that broke the whole app's first paint). Fixed with an explicit `.ts` extension on the import (`allowImportingTsExtensions` is already on). Same class of bug as D59's Jest-side "module ships both `.ts` and `.js`, extensionless imports must resolve to `.ts`" gotcha — a different tool (Vite, not Jest), same underlying dual-ship hazard; any future extensionless cross-boundary import of a dual-shipped file needs the same explicit-extension treatment regardless of which tool loads it. | DECIDED |
| SURVEY-PAGINATION | Lists paginated through the shared `Paginated` wrapper (root D103); frontend only, no migration, patch version bump. | Accepted |
| SURVEY-D9 | Builder conditions moved into each section (target = that section or its questions, source = a choice question in a DIFFERENT section; the API rejects a question showing/hiding its own section). The builder now drops rules whose question/section was deleted and validates titles/options/rules client-side — dangling rules were a cause of the `PUT /structure` 400. Added `reopen` (closed -> published) with a confirm step for close/reopen and an in-flight lock on the status buttons (a double-click on publish used to hit the close button that replaces it). Added `survey_surveys.closed_message` (migration 002): a closed survey's 404 body carries `closed` + the owner's custom text, shown instead of the generic "not available" text; draft surveys still return a plain 404. Version 1.0.2. | Accepted |
| SURVEY-D10 | **Archive, duplicate, zip export/import** (user request; version 1.1.0, migration 003). (1) Archive is `survey_surveys.archived_at` (NULL = active), NOT a 4th `survey_status` value — `ALTER TYPE ADD VALUE` is awkward inside a migration transaction and an archived survey should keep its draft/closed status. Archiving a published survey closes it; restoring never reopens it; an archived survey returns a plain 404 to respondents and cannot be published/reopened until restored. The archive list is a separate page (`/survey/surveys/archived`, `?archived=true` on the list endpoint). (2) Duplicate (`POST :id/duplicate`, perm `survey.surveys.create`) copies settings, sections, questions, options and rules of a survey in ANY status into a new draft with fresh UUIDs and never copies responses. (3) Export/import is a zip containing `survey.json` (`format: papp.survey.package`, `version: 1`); ids in the file are only internal references and every import mints new UUIDs. Responses are exported as data only (submittedAt, respondentEmail, answers) — user id, edit token, IP and user agent are deliberately left out. Import validates the file with the same DTO + `validateStructure` rules as a builder save, always creates a draft, and imports responses only when the importer ticks the box. New permissions: `survey.surveys.archive`, `survey.surveys.export`, `survey.surveys.import`; export WITH responses needs the existing `survey.responses.export`. The responses Excel export already existed (Responses page). | Accepted |
| SURVEY-D11 | **Sections are pages with Next/Back and "go to" navigation** (user request; version 1.2.0, migration 004). Each section stores `navigation` JSONB `{defaultTarget, routes[]}` — default `{}` = continue to the next section, so existing surveys behave as before but one section per page. A route is `{sourceQuestionId (a choice question of THAT section), sourceOptionValue, target}`; first matching route wins, else `defaultTarget` (`null` = next section, `'submit'`, or a later section id). Chosen over a 3rd `survey_logic_action` enum value (`ALTER TYPE ADD VALUE` is fragile inside the migration runner) and kept separate from show/hide rules, which still hide/show sections and questions. Targets must be LATER sections or submit — enforced in `validateStructure`, ignored by the engine — so navigation can never loop; Back follows the visited trail rather than recomputing. `resolveVisibility` now returns `pathSectionIds` and only sections on the walked path count as visible, so questions in skipped sections are neither required nor stored (the server uses the same engine). The public fill payload now includes section title/description/navigation. Required questions are checked per page on Next/Submit. Export/import and duplicate remap the ids inside `navigation`. | Accepted |
| SURVEY-D12 | **Microsoft Forms gap analysis and top-10 plan written, nothing built** (owner request: extend survey capabilities). `ROADMAP.md` inventories Microsoft Forms features per item (form, section, question, answers, quiz, sharing, results) against this module, marks confidence where only third-party sources were reachable, and proposes ten features in five phases: selection limits, "Other" choice, answer validation, description editors, shuffle (phase A, `config` JSONB only, no migration); schedule + response cap, thank-you/progress/receipt (phase B, migration 005); preview + QR/share (C); images (D); Likert (E). Findings worth acting on regardless: `opens_at`/`closes_at` exist but have no editor and are not enforced; section/question `description` is stored and shown but cannot be edited in the builder. Open decisions (image storage, survey settings column, question-type enum, list contents, bilingual surveys) are listed at the end of `ROADMAP.md`. Docs only, patch version bump. | Proposed |

Result: the top 10 stands; #1 (selection limits) is confirmed by both other tools and gets SurveyMonkey's full rule set plus an exclusive "None of the above"; #3 gains custom error messages; #6 is further justified by SurveyMonkey's response cap. | SURVEY-D14 | **Roadmap decisions answered by the owner** (2026-10-15). (1) Survey images (and later file uploads) are stored as files on a mounted disk volume served by the API, with a type/size allow-list; the volume must be backed up. (2) New survey-level settings go into one `settings` JSONB column (plus a real `response_limit` column), so future flags need no migration. (3) The question-type column becomes plain text once, in the first migration that adds a type; JSON is not used for the type name because each type's details already live in `config` JSONB. (4) Priorities are user-experience first: the top 10 is now validation with clear messages, checkbox selection limits, hint editors, preview, builder usability (duplicate/move/unsaved-changes), schedule + response cap, "Other", thank-you + progress, share panel (QR), images; Likert, shuffle, receipt, ranking, NPS and quiz mode are "next up" backlog. (5) Bilingual survey content is not needed. Supersedes the "Proposed" status of SURVEY-D12/D13 for the list and order. Docs only, patch version bump. | DECIDED (user) |
| SURVEY-D15 | **Phase A built (respondent essentials), version 1.2.4, no migration.** (1) All rules in ONE framework-free file, `backend/question-rules.ts`, used by the builder save, the submit path and the browser, so the message next to a field is exactly what the server would say and cannot drift (same idea as `logic-engine.ts`; `ResponsesService` itself cannot be unit-tested because it imports core from `apps/api/dist`, which is why the logic was moved out of it). (2) Settings are keys in the existing `config` JSONB; `SurveysService.validateStructure` now actually validates them (the docblock mentioned a `validateQuestionConfig` that never existed). (3) "Other" is the string `__other__:<text>` so logic rules, reports and every string-based consumer keep working; the cost is that a logic rule cannot branch on "Other" (accepted). (4) Selection limits support at-least / at-most / range / exactly-N and an exclusive "none" choice that stands alone and is exempt from the count; the respondent page disables boxes at the maximum and shows a live hint. (5) Text validation kinds: text (max length), number (integer, min, max), email, URL, each with an optional custom message; no regular expressions (ReDoS risk). All text answers also have a 10,000-character ceiling. (6) **Bug fixed on the way:** a scale starting at 0 (for example 0-10) was silently turned into 1-10 because `0` was treated as unset (`Number(min) || 1`); `scaleBounds` fixes it for builder, page and server, and scale/date/time answers are now range/format checked. (7) An empty selection (`[]`) now counts as unanswered, so a required multiple choice can no longer be satisfied by an empty array. (8) Hints: the builder gained editors for the section description, the question hint and the placeholder (columns already existed). Tests: unit (question-rules, validateStructure), component (respondent page), real-HTTP e2e (new `survey.e2e-spec.ts`). | DECIDED |
| SURVEY-D16 | **Phase B built (owner tools), version 1.2.5, no migration, frontend only.** (1) **Preview** reuses the real respondent code: `TakeSurveyPage`'s paging/validation/question rendering moved into `SurveyRunner`, so a preview can never drift from what readers see; the builder feeds it its on-screen structure (cleaned by the same `buildPayload` used for Save, so an incomplete survey shows the same translated error instead of a broken preview). (2) **Duplicate question / section**: fresh UUIDs for the question, its options and (for a section) its questions; titles get a translated " (copy)" suffix; logic rules and section navigation are deliberately NOT copied (they reference the original's ids). (3) **Move question to another section** appends it to the end of the target; a rule that would make it show/hide the section it now lives in is dropped (the API rejects that combination); stale go-to routes are already cleaned by `buildPayload`. (4) **Unsaved-changes guard**: dirty = JSON snapshot of the settings plus structure differs from the last load/save; covers tab close and in-app link clicks via a capture-phase listener, and the builder's Back button; uses `window.confirm` because the decision must be synchronous inside the click handler. Chosen over migrating the whole app to a data router (`useBlocker`) as far too large a change for this feature. (5) **Share panel**: QR drawn client-side (`qrcode`, already a web dependency), PNG for printing and SVG for design tools; the embed snippet escapes the title; no frame-blocking header exists on the platform, so embedding works (if one is ever added, this feature needs a deliberate exception for `/survey/:id`). | DECIDED |
