| SURVEY-D1 | **Ownership/access is plain RBAC** (new `survey.*` permission codes in the manifest), not a per-user "my surveys only" model — matches every other module. **Notify emails** (arbitrary admin-typed addresses) are a module-owned exception to root D21 (confirmed with the user: D21 scoped `NotificationsService`'s own targeting, not other modules). **Question types for v1**: short_text, paragraph, single_choice, multi_choice, dropdown, linear_scale, date, time, rating — file upload and question grids explicitly deferred to a fast-follow. | DECIDED (user) |
| SURVEY-D2 | `one_response_per_respondent` is a per-survey, admin-toggleable setting — cannot be a DB unique/partial index (a plain or partial index can't be conditional on a column in a *different* row). The first migration draft (schema-design phase) got this wrong with a partial unique index on `(survey_id, respondent_user_id)`; building the real submit endpoint against the real toggle surfaced the contradiction (a second submission with the toggle off would 500 on a raw Postgres constraint violation before ever reaching application logic). Fixed by dropping the index for a plain lookup index and moving enforcement entirely into `ResponsesService.submitAuthenticated`. Full writeup: root `D66`. | DECIDED |
| SURVEY-D3 | `SurveysService.replaceStructure`'s three `deleteMany` calls originally used a non-UUID sentinel (`['__none__']`) inside `notIn` to mean "nothing to keep" — Postgres rejects a non-UUID literal against a real `uuid` column even inside `NOT IN`, and this is common (any all-text-question survey has zero options; a section can have zero questions) not rare. Fixed with a conditional `where` (omit the `id` filter entirely when the keep-list is empty, rather than faking a value into it). Full writeup: root `D66`. | DECIDED |
| SURVEY-D4 | `ResponsesService.writeResponse` writes its own `audit_log` row **directly** via the real `AuditLogWriter` (injected from `apps/api/dist/core/audit/audit-log.writer`, `@Global()` so no extra module wiring needed), bypassing the usual `@Audit(...)` decorator on the controller. Deliberate: `submitPublic`'s response body carries a one-time raw edit token that must never reach a durable log, and the generic `@Audit` interceptor's fallback (log the whole handler response as `newValue` when no `fetchState` is given) would have logged it — and `fetchState` can't help either, since it never sees a freshly-created row's id, only the request. Same category of exception as `AuthService`'s own direct login/logout audit rows. | DECIDED |
| SURVEY-D5 | `AnswerInputDto.value: unknown` had no `class-validator` decorator at all, so the global `ValidationPipe`'s `whitelist: true` silently stripped every submitted answer's value before any service code ever saw it — a real bug that would have broken every response, in every deployment, forever. Found only via a full real-browser Playwright walkthrough (the report page showed "answered 0 times" despite a visibly-successful `201` submit); invisible to `tsc` and to direct-Prisma smoke tests. Fixed with `@IsDefined()` (permissive on purpose — real per-question-type shape validation happens later, in `ResponsesService.validateAnswerShape`, once the question's real type is known). Full writeup: root `D67`. | DECIDED |

Full writeup: root `D64`. | DECIDED |
| SURVEY-D7 | Respondent-facing fill is split into two controllers/endpoint families (`FillController` for a logged-in visitor, `PublicSurveyController` for none) rather than one conditional endpoint — `JwtAuthGuard` never populates `request.user` on a `@Public()` route even when a valid token was sent, so a single handler branching on "am I logged in" is structurally impossible. `TakeSurveyPage.tsx`'s one canonical `/survey/:surveyId` route picks the pair to call from the real `useAuth()` status. Full writeup: root `D65`. | DECIDED |
| SURVEY-D8 | `TakeSurveyPage.tsx`'s `import { resolveVisibility } from '../../backend/logic-engine'` (no extension) resolved, under Vite's real DEV SERVER, to the compiled `logic-engine.js` CommonJS sibling instead of the `.ts` ESM source that sits right next to it (D56's dual-ship convention) — Vite's default `resolve.extensions` checks `.js` before `.ts`. This threw `does not provide an export named 'resolveVisibility'` at runtime the moment the page's code actually executed in a browser; `npm run build`'s Rollup-based production bundling never surfaced it. Found via a real `vite` dev-server + headless-Chromium check done as part of root `DECISIONS.md` D78's own verification (that change made `discovery.ts` load every module's `routes.tsx`, and therefore this page, EAGERLY at app boot instead of only on navigation to `/survey/:surveyId` — turning a latent per-page bug into one that broke the whole app's first paint). Same class of bug as D59's Jest-side "module ships both `.ts` and `.js`, extensionless imports must resolve to `.ts`" gotcha — a different tool (Vite, not Jest), same underlying dual-ship hazard; any future extensionless cross-boundary import of a dual-shipped file needs the same explicit-extension treatment regardless of which tool loads it. | DECIDED |

| SURVEY-D19 | **Ext. E (second batch): safe text formatting, maths, video link, version 1.4.4, no migration.** Survey/section/question titles and descriptions accept a tiny inline markup — `**bold**`, `*italic*`, `[label](https://…)`, `{red\|text}` / `{#b00020\|text}` (six named colours or #rgb/#rrggbb), `$formula$` (KaTeX), `\` to show a character literally — written by hand or via a toolbar with live preview. The one raw-HTML spot is KaTeX's own output with `trust: false` (so `\href{javascript:…}` is inert) and a formula KaTeX rejects is shown as typed. `katex` is the one new dependency (apps/web). Colours are limited to a fixed palette-or-hex because arbitrary CSS would be an injection route. A question's video is a plain link (`config.videoUrl`, http/https, validated by `question-rules.ts`), never an embed (owner decision: no third-party player, no outside request until the reader clicks). | SURVEY-D20 | **Ext. F: piping and carry-forward, version 1.4.5, no migration.** (1) Piping: `{{q:<question id>}}` in a section title/description or a question title/description is replaced, on the respondent page, by the reader's earlier answer (option label for choices, "Other" text, plain value otherwise; "…" when unanswered or the source is hidden). The substituted answer is markup-escaped (`escapeMarkup`) BEFORE the text is rendered, so a reader typing `**x**` or a link into one question cannot format or link anything in the next page. (2) Carry-forward: a choice question can set `config.optionsFrom = { questionId, mode: 'selected' | 'unselected' }` and then has no options of its own: it offers the options the reader ticked (or did not tick) in an earlier choice question; "Other" text is never carried. (3) Rule: the source must be in an EARLIER SECTION (its answer is final once the reader moved on; going Back recomputes, and the page drops carried answers that are no longer offered), a carry-forward question cannot itself be a source, and cannot be the condition of a show/hide rule (checked in `piping.validatePiping`, run on every structure save). (4) When nothing is offered (e.g. "ticked" but nothing was ticked) the question simply does not apply — skipped even if marked required, and an answer sent for it anyway is dropped. (5) The server re-derives the offered options from the submission itself (only counting visible source answers) and validates the answer against them; it never trusts the page. (6) Reports count a carried question against all of its source's options; duplicate/import rewrite the ids inside `optionsFrom` and the tokens. `piping.ts` is import-free like `rich-text.ts` (SURVEY-D8). | DECIDED |
