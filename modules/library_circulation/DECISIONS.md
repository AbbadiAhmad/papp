# Library Circulation & Finance module — decisions & gotchas log

Append-only, same format as root `docs/DECISIONS.md` (see `docs/MODULE_SPEC.md` §9.2). Entries here are scoped to this module only — a platform-wide decision is cross-referenced by its root `Dnn` id, never restated.

| # | Decision | Status |
|---|---|---|
| LIBRARY_CIRCULATION-D1 | Fulfills root D44: one combined module (`library_circulation`) for both circulation and finance, `dependsOn: ["library_catalog"]`. Not split into two modules — the librarian's requirements treat them as one operational area (§12-14), and splitting would mean the finance tables referencing circulation's fines across a module boundary with no shared client benefit. | DECIDED |
| LIBRARY_CIRCULATION-D2 | A "student" is created by THIS module's `StudentsService.create()`, not by an admin first creating a core `User` and then linking it — the librarian's real workflow is "add a student" as one action. A random temporary password is generated server-side (never typed by the librarian) and returned ONCE in the create response with `mustChangePassword: true`; the `reader` role is assigned in the same transaction. This duplicates a small amount of core `UsersService` logic (argon2id hash, role assignment) rather than importing `UsersModule`/`UsersService` via the `apps/api/dist/...` cross-module-import pattern (root D64/D65) — a deliberate simplicity choice: no password-policy check is needed at all since the password is never operator-chosen, so there was nothing worth reusing from `assertPasswordMeetsPolicy`. If a future requirement needs the FULL admin-create-user flow (email invite, policy-checked custom password, etc.) reused here, that's the point to revisit this and import `UsersService` for real instead. | DECIDED |
| LIBRARY_CIRCULATION-D3 | `library_borrowings.status`/`library_fines.status` are `TEXT` + `CHECK`, NOT a Postgres `ENUM` — unlike `library_catalog`'s own `LIBRARY_CATALOG-D5` (which needed a real `ENUM` for its Prisma `enum` field mapping). Here, the Prisma model fields are plain `String`, not a Prisma `enum`, specifically so no `CREATE TYPE` is needed for a column this module owns end-to-end (simpler migration, same DB-level integrity via `CHECK`). Don't "fix" this to match `library_catalog`'s pattern without a real reason — they solve the same integrity problem two valid ways for two different reasons (that module maps to a Prisma `enum` type it exposes; this one doesn't need to). | DECIDED |
| LIBRARY_CIRCULATION-D4 | `overdue` is a valid status value with no code path that ever sets it — no scheduler/cron exists anywhere in this platform. Lateness for fines is computed at return time from `returnedAt - dueAt`, not from a persisted status transition. See `DOCUMENTATION.md`'s "Known gotchas" for what a future scheduler-backed implementation would need to change. | DECIDED (deferred) |
| LIBRARY_CIRCULATION-D5 | Scan prefix-dispatch (`docs/LIBRARY_MODULE_REQUIREMENTS.md` §6) implements STU/BOOK only, not STAFF/FINE — those two have no code scheme anywhere in the platform and aren't needed by the borrow/return flow itself (§7/§9's minimum steps only ever scan a student or a book). Built as an in-module utility (`CirculationService.scan()`), not extracted to a shared core "prefix-dispatch" platform capability as §6 floats as a possibility — YAGNI, only one module needs scanning today; extract it if/when a second module does. | DECIDED |
| LIBRARY_CIRCULATION-D6 | Transaction/receipt numbers (`TXN-YYYYMMDD-<8 hex>` / `RC-YYYYMMDD-<8 hex>`) are generated from the date + `crypto.randomBytes`, not a DB sequence/counter table — simplest way to satisfy "every transaction needs a unique number" (§12/§14) without a new shared-sequence mechanism; collision probability is negligible at this scale (4 bytes of randomness per day). | DECIDED |
| LIBRARY_CIRCULATION-D7 | Reporting/analytics (§18-20), Excel import/export (§15-17), global search (§24), batch code printing (§28), and academic-year CRUD (§34) are explicitly deferred, not built in this pass — see `DOCUMENTATION.md`'s "Known gotchas" for the full list and why each is a real, separately-schedulable follow-up rather than an oversight. Every flow that IS built (students, scan, borrow, return, fines, payments, receipts) is fully real end to end — no mock data, no partial/half-wired endpoint. | DECIDED (deferred) |
| LIBRARY_CIRCULATION-D8 | **Supersedes D6**: transaction/fine/payment/receipt numbers are now genuinely sequential, Postgres-`SEQUENCE`-backed (migration `002_add_readable_numbers_and_payment_method.sql`), formatted `<PREFIX>-000123` via `FinesService.nextNumber()` (`SELECT nextval(...)` inside the same DB transaction as the row it numbers). D6's date+random-suffix scheme was replaced once the librarian's own worked example (a companion, more detailed walkthrough — root D75) showed exactly this format ("FINE-000087", "PAY-000145") as what she expects to read/write down. Also added: `library_fines.fine_number`, `library_payments.payment_number` (neither existed before — a fine/payment previously had no human-readable reference at all, only a UUID `id`), and `library_payments.payment_method` (cash/card/transfer). | DECIDED |
| LIBRARY_CIRCULATION-D9 | **A module-local gap, not built**: no `library_classes`/grades lookup entity exists — `library_students.className` stays free-text. The librarian's Excel-import walkthrough (§15, root D75) implies class names need validation against a real known list ("Row 31: class not found"), but Excel import itself is still deferred (D7), so this entity has no consumer yet; building it now would be a table with nothing reading or writing it. Add it together with Excel import, not before. | ASSUMED (deferred) |
| LIBRARY_CIRCULATION-D10 | **Notification Center integration** (§23): `CirculationService`/`FinesService` now send real in-app notices to the student on borrow, return (including a late-return note), fine creation, and payment. Content is hardcoded Arabic text, not an operator-editable `system_settings` template like core's password-reset notice (root D22) — see root ASSUMPTIONS.md A15. Depending on the real core `NotificationsService` (imported from `apps/api/dist/...`, root D64/D65's exception category) broke both services' entire Jest unit-test suites at module-load time — fixed via the token-injection pattern in root D74 (`backend/notifications-sender.ts`); see that entry for the mechanism, and `.claude/skills/papp-add-feature/SKILL.md`'s gotcha #3 for the now-preferred general fix. | DECIDED |
| LIBRARY_CIRCULATION-D11 | **QR-code image generation (`qrcode` npm package) and camera-based scanning (`html5-qrcode`) are now built** — root ASSUMPTIONS.md A14 has the full "why module-local, not a shared package" reasoning (same YAGNI logic as D5's scan-prefix-dispatch). `QrCodeImage.tsx` renders a real QR image client-side from a student's own `code` (no backend endpoint needed — the value is already known). `CameraScanDialog.tsx` owns the real `getUserMedia()` camera lifecycle (`Html5Qrcode.start()`/`.stop()`, torn down on close so the camera light never stays on). `ScanPage` now offers all three of §6's input methods for real: camera, USB keyboard-wedge scanner (free — already just keystrokes into the same text field), and manual typing. | DECIDED |
