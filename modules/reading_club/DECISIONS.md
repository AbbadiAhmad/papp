# Reading Club module — decisions & gotchas log

Append-only, same format as root `docs/DECISIONS.md` (see `docs/MODULE_SPEC.md` §9.2). Entries here are scoped to this module only — a platform-wide decision is cross-referenced by its root `Dnn` id, never restated.

| # | Decision | Status |
|---|---|---|
| READING_CLUB-D1 | **`dependsOn: ["library_circulation"]`, not `["library_catalog"]`.** The user's request ("depend on library circulation module") maps directly onto the platform's real module boundary (root D44): "readers" in this module are `library_students` rows, which only exist once `library_circulation` is installed (which itself already requires `library_catalog`, transitively). This module never reads `library_catalog` tables directly — it has no need to, since it only cares about a reader's identity (`library_students`) and their return history (`library_borrowings`), both owned by `library_circulation`. | DECIDED |
| READING_CLUB-D2 | **Groups/stages are plain relational entity CRUD (own tables, own controller), NOT the manifest's `settings[]` mechanism** (`docs/MODULE_SPEC.md` §8), even though the user's own wording ("the librarian defines the groups, the stages... in the module settings") sounds like it. `settings[]` is for a single admin-editable JSON/scalar value per key (like `library_circulation.loan_policy`) — an orderable, growable list of stages per group, each with its own CRUD lifecycle and referential integrity (a stage can't be deleted once a reader has a history against it), doesn't fit that shape. `frontend/pages/StagesManagerDialog.tsx` (reached from the Groups page) is the real "module settings" surface the requirement asked for. | DECIDED |
| READING_CLUB-D3 | **A stage's `targetAmount` is that stage's own amount, not cumulative** — "stage 1 is 5 books, stage 2 is an additional 10 books" (the user's own example) is `targetAmount` 5 then 10, never 5 then 15. Every progress computation (`MembershipsService.computeStageProgress`) and the dashboard's stat aggregation both read it this way; don't "helpfully" sum prior stages' amounts anywhere. | DECIDED |
| READING_CLUB-D4 | **Progress is computed two different ways depending on the current stage's `targetType`, never a single mechanism for both.** `books`: counted LIVE (never stored) from `library_circulation`'s own `library_borrowings` table — `status = 'returned' AND returned_at >= stageStartedAt` for that reader — real data already owned by that module, zero manual entry, always fresh. `pages`: `library_catalog_books` has NO page-count column anywhere on this platform (confirmed by grep before building this), so there is no data source to compute it from automatically; it is the librarian's own manually-recorded `manual_progress_amount`, updated via `PUT /readers/:studentId/progress`. This is a considered v1 default, not something the user explicitly specified — flagged here in case a future page-count field on `library_catalog` should replace it; that would be a `library_catalog` schema change raised with the user first, not something this module should invent unilaterally. | DECIDED (flag: page-count auto-tracking would require a library_catalog change, not done) |
| READING_CLUB-D5 | **"Mark stage finished" and "confirm reward delivered" are two independent actions, not one**, closing a real ambiguity in the user's request (one sentence describes marking-finished-and-rewarding-and-advancing as a single librarian action; a separate sentence describes the circulation scan page later letting the librarian "confirm" the reward was handed over). Resolved as: `StageCompletionsService.markComplete` does snapshot-the-completion (`reward_status = 'pending'`) AND advance-to-the-next-stage together, in one transaction, the moment the librarian marks it — the reader's progression is never blocked on the physical present actually being in hand. `confirmReward` is a separate, later, idempotent-guarded action (rejects a second confirm on an already-`delivered` row) callable from either this module's own reader page or `library_circulation`'s scan-page hook — exactly the "librarian can confirm he handed the reader his present" flow, decoupled from progression so it can happen whenever the reader is next physically present, not necessarily the same moment they finished the stage. | DECIDED |
| READING_CLUB-D6 | **Cross-module frontend hook: a raw `apiClient` endpoint call in each direction, never a static cross-module TS import — in EITHER direction, regardless of which module `dependsOn` the other.** `frontend/circulationIntegration.ts` (this module calling `library_circulation`, the safe direction per `dependsOn`) and `modules/library_circulation/frontend/readingClubIntegration.ts` (that module calling THIS one, the architecturally backward direction were it a static import, since `library_circulation` does not and should not `dependsOn: ["reading_club"]`) both use the identical shape: a tiny local file with a minimal duplicated response type and a plain `apiClient.get/post(...)` call, never `import ... from '../../reading_club/frontend/api'`. This keeps both modules' frontend bundles free of a hard source dependency on a module that might not even be installed (the `library_circulation` scan-page hook is entirely optional/additive — hidden via `useModuleFrontendManifests` + a live permission check, never a hard requirement of that page). No generic "cross-module UI extension point" platform mechanism was built for this (unlike the reusable scan-prefix-dispatch idea `LIBRARY_MODULE_REQUIREMENTS.md` §6 floats) — this is the second real consumer of the pattern (the first being backend-to-backend direct-table-reads, `library_circulation`'s own `CirculationService` reading `library_catalog`), still not a third, so a shared framework stays YAGNI per the same reasoning `LIBRARY_CIRCULATION-D5` already used for scan-prefix-dispatch. See root `docs/DECISIONS.md`'s own cross-reference entry for this same call recorded at the platform level. | DECIDED |
| READING_CLUB-D7 | **A reader belongs to exactly one reading-club group at a time** (`reading_club_memberships.student_id` is UNIQUE) — "the librarian can move the reader from one group to another" is implemented as an upsert on the SAME row (`MembershipsService.assign`), not a new row per group. The reader's completion HISTORY from a prior group is untouched (`reading_club_stage_completions` rows are never migrated/deleted when a reader changes groups) — a reader's full reward history across every group they've ever been in remains visible on their detail page regardless of which group they're in now. | DECIDED |

| READING_CLUB-D10 | **Episodes (seasons/years) fully own groups, not a shared cross-episode config** — the user's explicit choice, confirmed twice: a group created in "Season 2024" belongs ONLY to that episode; starting a new episode never carries groups/stages forward automatically. `reading_club_groups.episode_id` is `NOT NULL`; `reading_club_stages` deliberately gets NO `episode_id` of its own — a stage's episode is always its own group's episode, reached via `group_id`, since duplicating it onto stages would be denormalized data that could drift (a stage row claiming a different episode than its own group would be a data-integrity bug with no legitimate meaning). `reading_club_memberships`/`reading_club_stage_completions` also carry their own `episode_id`, set to the TARGET GROUP's episode at assignment/completion time — not inferred transitively through `group_id` at read time — so a membership/completion's episode is a fast, directly-queryable column rather than requiring a join, and so history stays correct even if (hypothetically) a group's own episode_id were ever looked up differently later. Exactly one episode is ever `is_current = true` platform-wide (not per-group) — enforced by `CREATE UNIQUE INDEX reading_club_episodes_one_current ON reading_club_episodes (is_current) WHERE is_current`, the standard Postgres partial-unique-on-boolean-true idiom (verified against a real Postgres 16 instance, see READING_CLUB-D15 — a second `is_current=true` insert is rejected with `duplicate key value violates unique constraint`). | DECIDED |
| READING_CLUB-D11 | **Migration 002 deletes ALL existing reading_club data** (`TRUNCATE reading_club_stage_completions, reading_club_memberships, reading_club_stages, reading_club_groups RESTART IDENTITY CASCADE`) before adding the new `NOT NULL episode_id` columns. | READING_CLUB-D12 | **Episode read/write scoping**: every read endpoint that lists groups/readers/dashboard stats accepts an optional `?episodeId=` query param, defaulting to the CURRENT episode when omitted — this keeps every existing frontend call site working unchanged (an omitted param is the common case) while letting a permitted user browse a past, closed episode read-only. Every WRITE (create/update/delete group or stage, assign/move-stage/update-progress, mark-complete) is rejected with a `ConflictException` (409, message contains "closed") when the resolved episode is not current — enforced centrally via `EpisodesService.assertEpisodeIsCurrent(episodeId)`, called at the start of every mutating service method, never duplicated ad hoc. `createGroup`'s own `episodeId` is OPTIONAL in its DTO and defaults to the current episode when omitted (consistent with the "omitted = current" read-side default) — a caller only needs to pass it explicitly in the unusual case of programmatically targeting a specific episode. **Permission for `GET /episodes`/`GET /episodes/current`/`GET /episodes/:id` reuses `reading_club.groups.view`** rather than inventing a new read permission: everyone who can browse groups needs to know which episode is current and be able to switch to a past one (the episode switcher lives right next to the groups/readers/dashboard views it scopes) — a separate `episodes.view` permission would only ever be granted identically alongside `groups.view` in practice, so it would add a permission-matrix row with no real independent value. `POST /episodes` (starting a new episode, an irreversible-feeling action that closes the current one) stays behind the stronger, dedicated `reading_club.episodes.manage`. | DECIDED |
| READING_CLUB-D13 | **Book-entries auto-sync**: `MembershipsService.syncStageBookEntries` runs from `getReaderDetail` (the reader-detail-page GET, not a background job or a hook off `library_circulation`'s own return-flow) and inserts one `reading_club_stage_book_entries` row per `library_borrowings` row with `status='returned' AND returnedAt >= stageStartedAt` for that reader — the EXACT SAME window `computeStageProgress` already uses for books-type progress, so the book list and the progress count can never diverge. This applies to BOTH `books`-type and `pages`-type stages (user confirmed) — the sync condition is the stage time window, not the stage's `targetType`; a pages-type stage still gets its "books read this stage" list even though its progress number comes from `manualProgressAmount` instead. **Dedup is by `borrowing_id` existence regardless of status** — `WHERE borrowingId IN (...)` with no `status` filter — so a DISCARDED auto-entry is never re-inserted on a later page view; only checking `status='active'` rows would have re-created a librarian's deliberately-discarded auto-entry the next time the page loaded, defeating the point of discard. Since a GET needs an acting user for the new row's `added_by` and this codebase has no "system user" convention anywhere else, `getReaderDetail` now takes an optional `actingUserId` threaded from `@CurrentUser()` in the controller; passing `null` (used nowhere in this module today) skips the sync entirely rather than failing. Verified end-to-end against a real Postgres 16 database, including the "call getReaderDetail twice — no duplicate row" and "discard then call getReaderDetail again — still no duplicate, still discarded" cases (READING_CLUB-D15). | DECIDED |
| READING_CLUB-D14 | **Book-entry discard/delete permission reuses `reading_club.memberships.update_progress`** rather than inventing a new code — the closest existing permission in the manifest for "editing a reader's stage-tracking data" (its own description is literally "Record a reader's manual page-progress", and book entries are the same category of reader-stage bookkeeping). A brand-new module found itself needing a genuinely new capability here; the alternative (a dedicated `reading_club.stage_book_entries.manage`) was considered and rejected because every role that should ever touch book entries (`admin`/`library_assistant`) already gets `update_progress` too, and past-episode read-only browsing is enforced independently by the episode-current check, not by permission — so a split permission would track `update_progress` 1:1 with no independent grant ever occurring in practice, the same reasoning READING_CLUB-D12 used to decline a separate `episodes.view`. Every mutating book-entry endpoint (add manual / discard / delete) checks this one permission; the read endpoint (`GET .../book-entries`) reuses the broader `reading_club.memberships.view`, consistent with the rest of a reader's detail page. | DECIDED |
