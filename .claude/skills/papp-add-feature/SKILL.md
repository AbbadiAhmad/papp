# Adding a feature to papp — required pattern

Read these first if not already in context: `docs/ARCHITECTURE.md`, `docs/MODULE_SPEC.md`, `docs/FEATURE_TEMPLATE.md`, `docs/DECISIONS.md`. This skill is the enforceable checklist version of those docs — when in doubt, the docs are the source of truth and this skill should be updated to match, not the other way around.

## Before writing any code

0. **If the target module already exists, read its own `modules/<key>/DOCUMENTATION.md` and `DECISIONS.md` in full — before re-reading `ARCHITECTURE.md`/`MODULE_SPEC.md` even.** Those are whole-platform; this module's own files are what tell you what's actually different about it, what it already got wrong once and fixed, and what gotcha you're about to rediscover the hard way if you skip this. Full spec: `docs/MODULE_SPEC.md` §9.
1. Is this a **core platform** capability (users/roles/permissions/sessions/audit/i18n infrastructure itself) or a **module** capability (Library Catalog, Survey, Borrowing, Finance, or any future domain feature)? Modules never modify core tables directly; core never depends on a module.
2. Does the target module already exist? If yes, add to its manifest. If no, **copy `modules/template/` to `modules/<your_key>/`** (`docs/MODULE_SPEC.md` §10) rather than scaffolding from scratch — it's a real, verified-working module exercising every manifest option (permissions, `defaultRolePermissions`, `roleAccessPolicy`/`roleAccessLocked`, a `settings` entry, a nested `menu`, an authenticated route AND a public one) with one deliberately simple entity as the worked example; rename `template`/`Template`/`TEMPLATE` throughout (grep case-insensitively — there's no rename script) and replace `TemplateItem` with your real entity. Start its `DOCUMENTATION.md`/`DECISIONS.md` fresh from the beginning (step 0 above) — don't leave the template's own placeholder content in a real module.

## Every new endpoint must have

- [ ] A permission code declared in the module's `manifest.json` `permissions` array (never invent a code inline only in the controller) — **unless** it's a deliberate public route (next bullet).
- [ ] `@RequirePermission('<code>')` on the controller method (or class, if the whole controller shares one gate) — via `PermissionGuard`, applied alongside `JwtAuthGuard`. No endpoint is ever permission-check-free, including read-only ones, unless it's genuinely public.
- [ ] If the endpoint is meant to be reachable with no login (a shareable link, per `docs/MODULE_SPEC.md` §7): the matching frontend route has `"access": "public"` in the manifest's `routes` array, the backend method has `@Public()`, and any access rule is enforced in the service layer (not a permission check — there's no user to check). If it's a **write**, it must also use the shared `ThrottlerGuard` (`system_settings.security.public_endpoint_rate_limit`) — this is not optional, see `MODULE_SPEC.md` §6.
- [ ] `@Audit({ category, entityType, action })` on every create/update/delete endpoint. Read endpoints only get it if they expose another user's sensitive data.
- [ ] A `defaultRolePermissions` entry in the manifest for every base role (`admin`, `library_assistant`, `finance`, `reader`), even if the value is an empty array — explicit "no access" beats an implicit gap.
- [ ] **Never** a hardcoded role-name check (`user.role === 'admin'`, `roles.includes('finance')`, etc.) anywhere in feature/module code. The **only** exception in the entire codebase is the Permissions page's own guard, per `docs/ARCHITECTURE.md` §7.4 — if you think you need a second one, stop and raise it with the user instead of adding it.
- [ ] A permission-matrix e2e test per `docs/TESTING_STRATEGY.md` §2 covering all four base roles + anonymous — **unless** the base platform is still in its pre-Phase-9 build (see next section): write a Tier 1 unit test of the permission check instead, and note the deferred e2e coverage for the Phase 9 hardening pass.

## Test tiering (D37) — read this before writing any test

Per `docs/TESTING_STRATEGY.md` §0: while the base platform is being built (`docs/BUILD_PLAN.md` Phases 1–8), write **only Tier 1 tests** — fast unit tests with mocked dependencies (no Docker, no real DB, no browser) plus static/lint checks. Do **not** reach for Testcontainers, a really-booted app + real DB, or Playwright per-feature; that's Tier 2, deferred to the dedicated Phase 9 hardening pass so it's built once, against real CI Docker access, instead of fought repeatedly in a sandbox that can't run it. In place of Tier 2 coverage, demonstrate the feature actually works with a real manual/scripted smoke verification (curl or a scratch script against a reachable Postgres) and report the real output — this is reviewed but not committed as a test file. If you're working on or after Phase 9, this restriction is lifted — write full Tier 2 coverage as normal.

## Every new field that touches secrets

- [ ] Marked `@Sensitive()` at the Prisma field level (passwords, tokens, hashes, anything that shouldn't appear in the audit log). Verify the schema-scan test in `docs/TESTING_STRATEGY.md` §3 still passes.

## Every new admin-tunable policy/threshold

- [ ] Stored as a key in `system_settings` (`docs/ARCHITECTURE.md` §6.3) and read through the cached settings service — never a hardcoded constant, `.env` value, or magic number in code. Password policy and session/token lifetimes already follow this (D23/D24); any new one (a future notification-sending limit, an import batch size, etc.) should too unless there's a specific reason not to — raise it with the user if unsure.

## Every new UI page

- [ ] Copy goes through `t('module_key.namespace.key')`, never hardcoded strings, in **both** `locales/ar.json` and `locales/en.json` (or the full confirmed language set — check `docs/CHECKLIST.md` item 4 for the current answer) at the same time. A key added to one language file without the other fails the locale-completeness lint.
- [ ] Uses MUI components / logical CSS properties only — no `margin-left`/`text-align: left` literals that would break under RTL. Sanity-check the page renders correctly in both `ar` (RTL) and `en` (LTR) before calling it done.
- [ ] Dates and numbers go through the shared `formatDate`/`formatNumber` utilities (pinned Gregorian calendar, Latin/Western digits per D6/D7) — never a raw `toLocaleDateString()`/`toLocaleString()` call.
- [ ] Gates its actions with `usePermission('<code>')`/`<Can permission="...">`, matching exactly the backend permission code for that action — this is a UX nicety, the backend guard is what actually enforces it, but they must never drift apart.

## Every new/changed module manifest

- [ ] `compatibleAppVersion` set to a sane semver range.
- [ ] `migrations` are additive, filename-ordered, never edited once applied (checksum-tracked) — a change to already-shipped behavior is a new migration file, not an edit to an old one.
- [ ] `menu` entries have a valid `parentId` (or `null`) and a `requiredPermission`.
- [ ] `roleAccessLocked` is used only when a role must **never** be grantable this module's permissions under any circumstance — this is rare; default is that admin can grant anything to any role.

## Known gotchas (learned the hard way — read before you hit them again)

- **`ValidationPipe`'s global `whitelist: true` silently STRIPS any request-body property whose DTO field has NO `class-validator` decorator at all** — not just an unrecognized property, a *declared but undecorated* one too. A field typed loosely on purpose (`value: unknown`, because its real shape depends on something looked up later, e.g. a question's type) still needs a decorator to survive — `@IsDefined()` is the right minimal choice when you deliberately don't want to constrain the shape yet. This is invisible to `tsc` (the TS type is fine) and to a raw-Prisma smoke test (never goes through the real HTTP pipe) — only a real HTTP call (curl or a browser) through the real running app will show the property silently missing on the other side. Found via `docs/DECISIONS.md` root D67; if a submitted value "disappears" with no validation error at all, check this first.
- **Prisma's `deleteMany({ where: { id: { notIn: [...] } } })` cannot use a non-UUID sentinel (`['__none__']`) to mean "empty keep-list" when `id` is a real `uuid` column** — Postgres rejects the non-UUID literal even inside a `NOT IN` list, and an empty options array / a section with zero questions is a common, not edge, case. Use a conditional `where` instead: full `{ ...scope, id: { notIn: keepIds } }` when `keepIds.length`, otherwise just `{ ...scope }` (delete everything in that scope). Root D66 has the concrete story.
- **A per-row uniqueness rule that's admin-toggleable (e.g. "one response per respondent" on/off per survey) can never be a DB unique index/constraint** — a plain or partial index can't be conditional on a column in a *different* row/table. Enforce it in the service (query-then-decide) instead, gated by the toggle; keep a plain (non-unique) index for the lookup's own performance. Don't reach for a unique constraint just because "at most one" sounds like a uniqueness problem — check whether the "at most one" is actually conditional first.
- **Modules import real core classes from `apps/api/dist/...` (never `src/`) for anything that's genuine shared logic, not just a metadata marker** — `PublicThrottlerGuard` (D57) started this category; `NotificationEmailService`/`NotificationsModule` (root D64/D65) extended it. A `@Global()` core module's exported providers (`AuditLogWriter`, `NotificationsService`, ...) are injectable into a module's own `@Module({imports: [...]})` via ordinary Nest DI with **zero** extra wiring — Nest builds one shared DI graph across `AppModule` + every discovered module (`main.ts`'s `RootModule`), so this isn't a hack. **But**: a Jest **unit** test that imports anything which transitively imports one of these `apps/api/dist/**` files CANNOT run under this repo's current test runtime — a compiled `.js` file's own `require('@nestjs/common')` (an ESM-only package) throws under Node's CJS loader, regardless of how the *test file itself* is transformed. If a service needs this kind of dependency, unit-test the parts of it that don't touch the dependency directly (pull pure logic into its own framework-free file the way `logic-engine.ts` does, or unit-test a sibling `.ts`-only service with no dist imports) and cover the rest with a real e2e/browser test instead — see root D68's item 3 for the full repro.
- **`modules/**` has no lint coverage from any tool in this repo** (`lint-permissions`/`lint-no-hardcoded-roles` scan `apps/api/src/**` only; both `apps/api` and `apps/web`'s ESLint flat configs structurally ignore any file outside their own directory — confirmed, not just unconfigured, root D68 item 0) **and no unit-test coverage unless the spec file physically lives under `apps/api/test/modules/<key>/`** and imports the module's `.ts` source by relative path (`jest.unit.config.ts`'s `testMatch` never reaches `modules/**` directly). `lint-locales.ts` is the one exception — it already discovers `modules/*/locales/{ar,en}.json` generically. Until this is fixed platform-wide (a real decision for the user, not something to slip in per-module), rely on `tsc --noEmit` + manual review for lint, and `apps/api/test/modules/<key>/*.spec.ts` + a real Playwright e2e spec for tests.
- **An MUI `TextField`/`Select` needs its own `label` (or `aria-label`) prop to have a real accessible name — a sibling `<Typography>` heading placed next to it does NOT count**, even though it visually reads as labeled. Found building `modules/template`: a status dropdown with only a nearby `<Typography>` rendered and worked fine by mouse, but a real Playwright `getByLabel(...)` walkthrough couldn't find it at all (root `D69`'s companion module log, `TEMPLATE-D4`) — the same gap a screen-reader user would hit. Give every form control its own real `label`, always.
- **`roleAccessPolicy`/`roleAccessLocked` and the generic per-module Settings-screen surface `docs/MODULE_SPEC.md` §8.3 describes are BOTH currently inert/nonexistent** — confirmed by grep, root `D70`/`D71`. Don't rely on a role lock actually blocking a grant, and don't expect a module's `settings` entries to get an admin-editable UI for free; a module needing an editable setting provides its own minimal endpoint (see `modules/template/backend/settings.service.ts`'s docblock for the working pattern).

## Before calling a module change done

- [ ] `modules/<key>/DOCUMENTATION.md` reflects the current shape (new table/permission/route/gotcha) — it's a living reference, update it now, not "later."
- [ ] `modules/<key>/DECISIONS.md` has a new entry for any real call you made, gotcha you hit, or bug you found and fixed — append-only, written as you go, same discipline as the root `docs/DECISIONS.md`. Never restate a platform-wide decision already in the root file; cross-reference its `Dnn` id instead.

## If you find yourself wanting to deviate from any rule above

Stop and ask the user rather than quietly doing something different — these rules exist specifically so that features built across different sessions/agents stay consistent. If a rule genuinely doesn't fit a new situation, propose the specific edit to this file (and the relevant `docs/*.md`) for the user to confirm, per the self-improvement process in `docs/CHECKLIST.md`.
